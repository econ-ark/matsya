# Matsya developer guide

> [!summary]
> Matsya is a service with two modes. In **architect mode** it reads a paper or a typed description of a dynamic economic model, writes the model's declaration in [Bellman-SYM](../../wiki/sym.md), the project's language for staged Bellman problems, as stage files together with a prose description of the model, and checks the two against each other; in **conversation mode** it answers questions with passages retrieved from an index of the project's documents and literature, with one literal excerpt of a passage or, when the configuration enables the optional conversation role, with a language model's answer to a question asked in a session, each claim of which cites material supplied to the language model and quotes it. Its program is fixed code in two packages. Everything that training revises, the instruction texts, the settings and the Matsya handlers, is data in one configuration folder outside the packages; training changes nothing in the language models themselves. Section 3 lists which page of the guide answers which question.

> [!info]- Relationship with other documents
> **Builds on** — the governing document [[matsya-meaning-map-meta-build]], which defines the objects, the maps and the training loop, and the dev-spec, the versioned development specification, [[spec_0.3-matsya]], whose requirements the build realizes.
> **Used by** — the [Matsya user guide](../user-guide/index.md), which names the three parts, matsya-client, matsya-architect and matsya-master, and follows one piece of work through the command `matsya`; the access instructions distributed with the service give the installation, the environment variables and a Matsya token; the operator's deployment instructions describe installation on the DigitalOcean server, a rented virtual machine that runs the service.

## 1 Program and configuration

Matsya consists of two kinds of thing, and the kind a change alters determines where the change is made and whether a **training pass** may make it. A training pass is one round in which a revised configuration is run on a set of papers, its results are measured against those of the configuration in use, and the revision is accepted or refused under the governing document's acceptance rule; the language models themselves are not changed.

The **program** is fixed code, tested by the packages' own tests (`venv/bin/python -m pytest packages/matsya/tests`, 282 tests on 9 October 2026) and changed only through an amendment of the dev-spec, a change to its document built with its own brief, the instructions for that one task. It has two packages. `packages/matsya` is the **frame**: it holds the web service and the retrieval code, loads and checks the configuration, and builds for each job the **job frame**, the record (the class `Frame` of `frame.py`) through which a Matsya handler uses everything else. The job frame gives a Matsya handler the function that sends a message to the language model's provider, the retrieval index, the Bellman-SYM elaborator `BellmanSYMDeclaration_to_ElaboratedSemanticObject` (the program that checks stage files with the `bellman` package's functions and constructs from them the elaborated semantic object $E$, the complete typed statement of the problem the files state: an [elaborated stage](../../wiki/elaborated_stage.md) for one stage file, an [elaborated trellis](../../wiki/trellis.md#the-syntactic-and-the-elaborated-trellis) for several), the comparator and the job's record. `packages/meaning-map-training` holds three programs: the **comparator** (`compare.py`), which decides whether two elaborated semantic objects have the same meaning and which a job uses as `ElaboratedSemanticObject_comparator` through `compare_outcomes` of `meaning.py`; the **form check** (`form_check.py`), which tests whether a description has the required headings and length; and the program that measures a training pass (`round_trip.py` and `round_trip_eval.py`). The program also fixes the **slots** that training fills, that is, the names under which the configuration must supply its contents and the form each content must take: the seven **role** keys (a role is one of the seven tasks given to a language model under an instruction text, such as `SourceMaterial_to_BellmanStageProse`, the Model-prose-writer, which writes the model prose from the source, or `BellmanStageProse_judge`, the judge), the thirteen Matsya handler names with their parameter lists, and the fifteen keys of the settings file with their types; and, for the optional **conversation role**, which a configuration enables by naming it among its roles, one more role key, `conversation_answer`, one more Matsya handler name, `conversation_reply`, and two more settings keys, `conversation_rounds` and `conversation_pages`, which the program requires together with the role's instruction text and refuses in a configuration that does not name the role. It answers the requests that the Model-prose-writer and [Prose-to-Bellman-Sym](../../wiki/bellman_sym_writer.md) may make for further documentation through the reading controller, which holds each role within the allowances of the settings' `reading` and places in a message only passages of the collections the user's grants allow, the public collections for every user and each private collection under a grant, whether or not a passage is marked `model_prompt` ([What Matsya reads](02-what-matsya-reads.md) §5). It counts the language-model tokens of every message before the message is sent (a token is the unit of text, a word or part of a word, in which a provider counts and prices a message) and holds each job, and each turn of conversation mode, within the token ceilings of the settings, which a training pass does not change ([What Matsya reads](02-what-matsya-reads.md) §4). It also fixes what a Matsya handler may report: the six kinds of event and their fields (`_EVENT_FIELDS` in `jobs.py`), the 27 validation codes, the names under which a Matsya handler reports that a language model's answer lacks the required structure or evidence (`MODEL_VALIDATION_CODES` in `frame.py`) and the fields of a request (`REQUEST_FIELDS` in `processor.py`).

The **configuration**, by contrast, is one folder of data, `operations/matsya/configuration/` inside the repository's internal folder `AI`, whose location the service reads from the environment variable `MATSYA_CONFIGURATION`. The governing document writes it as $\mathfrak{K} = (\mathfrak{t}, \mathfrak{s}, \mathfrak{h})$: the instruction texts $\mathfrak{t}$, one file per role under `texts/`; the settings $\mathfrak{s}$ in `settings.json`; and the Matsya handlers $\mathfrak{h}$, the Python functions that run a job, in the module `matsya_handler.py`, the name the constant `HANDLERS_FILE` of the configuration loader (`configuration.py`) requires (decision D-M19 of 8 October 2026, [[spec-0.3-dev-spec-decisions]]). A training pass revises this folder and never the packages. The folder also holds three reference guides, saved copies of published documentation pages that the Matsya handlers include in a language model's message, and `manifest.json`, which lists the SHA-256 **digest** of every other file (a digest is a 64-character code computed from a file's bytes, which changes whenever any byte changes). The program checks the folder against the manifest when the service starts and again at the start of every job, and refuses a folder that fails any check as a whole, so that no language model is called under an unchecked configuration.

## 2 The path of one job

A job of architect mode starts from a request to `POST /v1/model-iterations`, which contains a source, either `{"kind": "description", "text": ...}` or a paper as numbered pages or a base64 PDF, and may contain `max_cycles` (the cycle limit, at most `cycle_maximum`), `starting_declaration` (file names with their texts, elaborated in place of the Bellman-SYM writer's first call), `model_key` and `source_cluster` (two labels; a source whose `source_cluster` in the list of indexed sources equals either is left out of the job's searches and requests, so that the paper's own text is not retrieved for it, and without them every clustered source is left out), `target_formulation` (the one formulation of the model to write when the source states several), `session` (a named conversation with Matsya, a record of numbered entries, whose entries up to the session's revision when the job starts the job takes as its source, an answer of Matsya among them only when the user accepted it; a job of a session continues the session's earlier job, whose identity it records) and `force` (write even when preparation ends with open questions). The service's function for this route checks the request against the configuration's `cycle_maximum`, writes a job to the job database and passes it to the job runner, which runs at most two jobs at the same time. The caller receives a job identity and reads the job's state, its label (the session's name, the version of the session's text the job was built from, the job's number in the session and its state), its progress and its result from `GET /v1/model-iterations/{job_id}`, and may cancel a queued or running job with `POST /v1/model-iterations/{job_id}/cancel`: a queued job never runs, and a running job stops before its next call of a language model, a call already sent finishing and being charged, and ends `cancelled`.

The job runner calls the processor, `ModelProcessor.process` in `processor.py`. The processor checks the request again, loads and checks the configuration folder, turns the source into a `Source` record through the Matsya handler `normalize_source`, builds the job's language-model token ledger, the account of the tokens charged to each call, from the settings' `ceilings`, takes the retrieval index once for the whole job, builds the job frame from the texts, the guides, the settings, the function that sends a message to the provider, the job's record as begun by the processor, the job runner's progress callback, the index and the source, and calls the Matsya handler `cycle`. From here on the configuration's code runs the job and the program only answers its calls.

The Matsya handler `cycle` runs preparation first: a search of the index built from the concepts the source material names gives the passages that the source preparer and the Bellman-SYM writer receive, the source preparer writes the description $M$ of the model from the source, the judge compares $M$ with the source, and a preparation that ends with questions returns them to the caller as `needs_input` unless the request was forced. The source preparer and the Bellman-SYM writer may answer a call with a request for a further guide page or index passage, which the reading controller answers within the role's allowances and places in its next message. Then `cycle` runs cycles, up to the cycle limit, each consisting of writing (the Bellman-SYM writer writes the stage files $D$ from $M$, the Bellman-SYM elaborator constructs the elaborated semantic object $E$ from them, and its refusal is sent back to the Bellman-SYM writer), prose writing (the **dossier**, the numbered printed description of $E$, is written, the prose writer writes the description $M'$ from it, and the form check tests whether $M'$ has the required headings and length), judging (the judge compares $M$ and $M'$ in both orders on ten economic items, among them the state space, the shocks, the constraints and the parameters) and reconstruction (the Bellman-SYM writer writes stage files from $M'$ and the comparator compares their elaboration with $E$). A cycle converges when the comparator finds the two elaborations equal, the judge agrees, every block carries at least one `# from:` sentence and each occurs in $M$, and the Bellman-SYM writer's note `note.md`, in which it states the gaps it could not resolve, says `none`; otherwise the judge's tables, the comparator's [profile](../../wiki/judge.md), the unsupported citations and the unresolved note are sent to the Bellman-SYM writer in the next cycle, and a job that uses up its cycles ends `not_converged`. The record of the job keeps every language-model call as a digest and token counts, never as text, together with the configuration's version and digests, so that a run is attributed to one configuration, and keeps under `usage` the count of each message before its call and the tokens charged to the job, and under `reading` the identities of the pages and passages each message held and the status of each request. A call that would carry the tokens charged to its role or to the job past a ceiling of the settings is refused before it is sent, and the processor then ends the job `not_converged` with the reason `token_ceiling_reached`, whatever the Matsya handlers do.

The objects and the maps of the round trip, and the iteration of $M$, are defined in the governing document [[matsya-meaning-map-meta-build]] §1. The source material $P$ (SourceMaterial) is prepared into the description $M$ (BellmanStageProse); $M$ is declared in the stage files $D$ (BellmanSYMDeclaration); and their elaboration is the elaborated semantic object $E$ (ElaboratedSemanticObject). The prose writer's description $M'$, the declaration $D'$ written from it and the elaboration $E'$ of $D'$ are the three objects of the reconstruction. Four roles and two programs compute the maps. A role's adopted name is its key in the program; the two programs keep their function names and state the adopted name in their docstrings.

| Concept | Symbol | Adopted name | Arrow | Computed by |
|---|---|---|---|---|
| the source preparer | | `SourceMaterial_to_BellmanStageProse` | $P \to M$ | a language model under its instruction text |
| the Bellman-SYM writer | $\Upsilon_0$ | `BellmanStageProse_to_BellmanSYMDeclaration` | $M \to D$; in reconstruction $M' \to D'$ | a language model under its instruction text |
| the Bellman-SYM elaborator | $S$ | `BellmanSYMDeclaration_to_ElaboratedSemanticObject` | $D \to E$, or a refusal | `elaborate_files` of `meaning.py`, which calls `elaborate_text` and `elaborate_trellis` of the `bellman` package |
| the prose writer | $\Upsilon_1$ | `ElaboratedSemanticObject_to_BellmanStageProse` | $E \to M'$, from the dossier and nothing else | a language model under its instruction text |
| the judge | $J$ | `BellmanStageProse_judge` | $(M, M') \to$ a table of agreement on ten items; in preparation also $(P, M)$ | a language model under its instruction text |
| the comparator | $\cong$ | `ElaboratedSemanticObject_comparator` | $(E, E') \to$ a comparison profile, the items on which they differ | `compare_outcomes` of `meaning.py`, over the comparator of `packages/meaning-map-training` |

The wiki pages [Bellman-SYM writer](../../wiki/bellman_sym_writer.md), [Prose writer](../../wiki/prose_writer.md) and [Judge](../../wiki/judge.md) define the three maps a language model computes in a cycle.

**A turn of conversation mode.** When the configuration enables the conversation role, a question asked in a session through `POST /v1/sessions/{session_id}/turns` is appended to the session as an entry of the user and answered in a **turn**, which runs on a runner of its own with two workers, so that a running job does not delay an answer. The **turn runner**, `TurnRunner` of `conversation.py`, loads the configuration, fixes the snapshot of the index the turn reads, binds the reading controller to it, to the collections the person asking may read and to the conversation role's allowances, elaborates a stage file the question names, and calls the Matsya handler `conversation_reply`, which searches once from the question, calls the role and has the controller answer its requests. The turn runner then checks the answer: every citation must name material supplied to the role in the turn and quote it. It appends the answer, or the role's questions for the user, to the session and stores the turn's record, which holds digests, identities and counts and no message text. An answer of the role enters the source material of a later job only when the user accepts it with an entry of the kind `acceptance`.
