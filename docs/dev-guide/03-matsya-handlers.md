# The Matsya handlers

> [!summary]
> A **Matsya handler** is one of the thirteen Python functions, each with a name and parameter list that the program fixes and checks, that together run a job; the program calls two of them directly, `normalize_source` and `cycle`, and `cycle` calls the rest. A configuration that enables the optional conversation role holds a fourteenth, `conversation_reply`, which the turn runner calls once for each turn of conversation mode (§7). They are written in the Matsya handler module of the configuration folder, outside the package, because they are the trained code $\mathfrak{h}$: a training pass may rewrite what a Matsya handler does, and the program checks only that the thirteen names, and the fourteenth where the role is enabled, and their parameter lists are present. The word is not the Rosetta-stone **handler**, which names a solver that realizes an operator; the wiki page [Handler](../../wiki/handler.md) defines that sense and [Matsya handler](../../wiki/matsya_handler.md) this one.

## 1 Where the Matsya handlers are and what they may use

The module's file name is fixed by the program: `HANDLERS_FILE = "matsya_handler.py"` in `configuration.py`, which `check_files` requires; the qualifier distinguishes these functions from the Rosetta-stone handler (decision D-M19 of 8 October 2026). The module has 2,210 lines: the thirteen Matsya handlers, one for each **slot** (a slot is a Matsya handler name with its ordered parameter names, as `SLOTS` in `configuration.py` fixes them), and the optional fourteenth, `conversation_reply`, the slot of `OPTIONAL_SLOTS`; two public functions besides, `structure_of`, which reads the structure a description states under its heading Structure, and `target_question`, the fixed question of a job whose target cannot hold that structure; 47 helper functions whose names begin with an underscore; one helper class `_Calls`; eighteen public constants, among them the two lists of concepts from which an initial search is built (`LANGUAGE_TERMS` and `ECONOMIC_CONCEPTS`), the conversation role's key, guides and named fields (`CONVERSATION_ROLE`, `CONVERSATION_GUIDES` and `CONVERSATION_FIELDS`) the fixed headings `STRUCTURE_HEADING` of the description and `FILL_HEADING` of a recipe's note, `ROUND_TRIP_RULES`, what the files of a target cannot state, and `SOURCE_KIND_LABEL`, the label under which the Model-prose-writer's message names the kind of the source material; twelve private compiled regular expressions, two of them the headings of a paper in Markdown and in LaTeX, the tuple `_LATEX_LEVELS` of LaTeX's sectioning commands by rank, the two tuples of patterns compiled from those lists and the sets `_ANSWER_FIELDS` and `_SUBMIT_FIELDS` of the fields of the conversation role's answer and of its `submit_job`. Its docstring states the rules it is written under: a Matsya handler receives the job frame and uses the `bellman` package, the comparator, the form check and the exception classes through it; a Matsya handler calls a language model only through the Matsya handler `call`; and the module imports only the standard library, plus, for `normalize_source` and `select_pages`, two of the four Matsya handlers whose parameter lists have no `frame` parameter, the package modules `matsya_service.guide_pages` and `matsya_service.source`. Nothing enforces the import rule: the loader only imports the module.

The program calls two Matsya handlers by name, `normalize_source` to turn the request's source into a `Source` record and `cycle` to run the job. The other eleven run only when `cycle` or another Matsya handler calls them. The turn runner calls `conversation_reply` by name for each turn (§7).

Of the thirteen Matsya handlers, five, `prepare`, `write`, `verify_distribution`, `prose_write` and `judge`, call a role, each through the Matsya handler `call`, which sends the message; `cycle` calls the roles only through these five; and `compare`, `citations`, `unresolved_note`, `writer_references`, `select_pages` and `normalize_source` call none. The judge has two uses in a job: in preparation, to compare the prepared description with the source, and in each cycle, to compare the description $M$ with the prose writer's $M'$. The optional `conversation_reply` calls the conversation role through `call` and, for a stage file the turn names, the prose writer through `prose_write`.

## 3 The sequence inside `cycle`

`cycle` runs `prepare` first, which binds the reading controller to the source preparer, runs `writer_references` for the job's initial search and keeps its passages on the job frame as `references` for the Bellman-SYM writer, which receives them when it writes from $M$; in reconstruction `write` receives no passages and makes its own initial search from the concepts of $M'$. A preparation that ends with questions returns them as `needs_input`, unless the request set `force`, in which case the source material itself is given to the Bellman-SYM writer as the description and the questions and the Bellman-SYM writer's assumptions are recorded. A preparation that accepts the description holds the structure the description states under its heading Structure, the period templates with the keys of their stages, and its level, the smallest target that holds it, which the record keeps as `structure`; `cycle` compares that level with the job's target before any writing call, and a target that does not hold it, a target `stage` for a description of three stages or `period` for one of two period templates, ends the job `needs_input` with one fixed question, which names what the description found and the targets that would hold it (`target_question`), and no file is written; a wider target is admitted. When the description names income only by a general distribution function, `verify_distribution` runs before the first cycle. Each cycle then runs `write`, `prose_write`, `judge`, `write` again from $M'$, which is the reconstruction, and `compare` between the elaboration of the first files and that of the reconstruction. When the request supplied a starting declaration, the first cycle elaborates it in place of the Bellman-SYM writer's first call, sends it to the Bellman-SYM writer as `the refused files` and `the refusal` when the Bellman-SYM elaborator refuses it, and, when its elaboration reports a distribution that prevented the construction of a forward builder, runs a repair call of `write` at once when the variable is not named in the description, otherwise runs `verify_distribution` and then a repair call of `write` when the law is specified, or ends the job `needs_input` with the check's question when it is missing or unclear. A cycle converges when the comparator finds the two elaborations equal, the judge agrees (or is absent, or `judge_ends_cycle` is false), every block carries at least one `# from:` sentence and `citations` finds each of them in the description, and `unresolved_note` is false; the reason recorded is `source_agreement_and_semantic_fixed_point`. Otherwise the judge's answers, the comparator's profile, the unsupported citations and the unresolved note are sent to the Bellman-SYM writer in the next cycle as `economic differences to correct`, and a job that uses up its cycles ends `not_converged` with the reason `cycle_limit_reached` and the last cycle's files. A preparation, a writing or a reconstruction that ends with a request when no request round remains ends the job `not_converged` with the reason `request_rounds_exhausted`, with the files of the cycle's writing, or of the writing's earlier rounds, and never a request's text read as files. A call that would carry the language-model tokens charged to its role, or to the job, past a ceiling of the settings is refused by the program before it is sent, with the exception `CeilingReached`, which the job frame does not offer to the Matsya handlers, and every later call of the job is refused in the same way; whatever `cycle` then returns or raises, the processor ends the job `not_converged` with the reason `token_ceiling_reached`, keeping the calls and cycles of the record and removing any files of a model folder (`artifacts`).

Inside `prepare` and `write` every call of the role goes through the helper `_requests`, the loop of AMD-MAT-005 §5. The message holds the cached prefix (the instruction text and the guide pages the settings name), then the reading controller's parts (the retrieved passages, the addresses the role may request with its remaining allowances, and the material its requests added with their outcomes, each item once), then the task's input, the formulation, the job's target and, for the writer, the structure the description states, and any correction feedback, which stand in every message of the invocation. `_requests` examines each answer for the request form before the role's own parsers; a request is answered by the controller, which consumes a request round and no ordinary round, and the role is called again with the result; the first ordinary answer goes to the role's parsers and consumes one of `preparer_rounds` or `writer_rounds`. When the role answers with a request and no request round, or no ordinary round, remains, the controller executes nothing and `_requests` returns `None`, which ends the invocation with `request_rounds_exhausted`.

The writer returns the files of the job's target and no other, which the job frame's `elaborate_files(files, target)` checks: for a stage, one stage file `<key>.bl` and the note `note.md`, elaborated as one text; for a period, the stage files and `period.yml`, elaborated as a trellis of that period repeated twice and then held, printed and compared as its one period; for a trellis, the stage files, a period file for each period template, `period.yml` or `period.<name>.yml`, and `trellis.yml`, elaborated as a trellis; and for a recipe, the files of a trellis, the recipe `spec.yml`, a methods file `stages/<key>/methods.yml` for each stage the description says how to solve, `calibration/<model>.yml` and `settings/<model>.yml`, written into a temporary folder in the model folder's layout and read by the Bellman factory's `load_recipe` with no fill, then elaborated and bound by `specify_trellis` with the kinds of binding the recipe holds, so that a calibration whose slot `$fill` stands unbound, or a stage without a methods file, is checked for what it holds. A recipe is held, printed and compared as the trellis of its elaborated stages, since its methods, calibration and settings are read from files and not written back into prose. A converged job's `artifacts` place each stage file under `declaration/stages/<key>/` and every other file but the note under `declaration/` at the path its name writes, which puts a recipe's methods files in their stages' folders.

Each cycle's record holds its number, the writing (rounds, files, citations, digest), the prose writing, the judging, the reconstruction, the comparison, whether the citations were supported and whether the note was unresolved. The steps are reported to the job runner under the names `preparation`, `writing`, `prose_writing`, `judging` and `reconstruction`, and every language-model call is recorded as an event with the role, the message's digest and length, the answer's digest, the language-model token counts and any provider failures. The job runner's progress callback stops a job its user cancelled: at the first report after the request it raises the program's exception `JobCancelled`, so that a call already sent finishes and no further call starts, and the processor ends the job `cancelled` with the calls, the cycles and the usage its record holds (AMD-MAT-008 §4); a Matsya handler lets that exception pass, as it lets a refusal at a ceiling pass. The processor writes the reading controller's record into the job's record under `reading`: for each invocation of `prepare` or `write`, its role, step and cycle, its allowances, the concepts its text named, its initial search or reuse with the query used, its actions (`search`, `reuse` and `follow_reference`) with their reasons, the rounds and searches it used and why it stopped, and for each call, matched to the call's record by the message's digest, the identities of the pages, sections and passages its message held and the status and reason of the request its answer made; the record holds no text.

The job store keeps this record whole, and the route `GET /v1/model-iterations/{job_id}` returns it in one of two views (AMD-MAT-010 §3). The products view, the default, holds the job's products and what a report on them needs: the job's target and the structure its description states, the status and the reason, the model prose (`description`), the questions, the paper checks, `cycles_run`, and `last_cycle`, which holds the last cycle's files, its judging reports, its comparison reduced to `equal` and `first_difference`, and whether its note was unresolved; `reading` is reduced to the index digest and the guides, and `usage` to the language-model tokens charged to each role and to the job with the number of calls of each role. It holds no call, no invocation of the reading record and no earlier cycle. The full view, `view=full`, is the record as the job store holds it, which training reads. The products view is computed by the program's function `products_view` of `processor.py` from the entries the cycle controller writes, `writing.files`, `judging`, `comparison` with its `profile`, and `unresolved_note`; a Matsya handler that writes a cycle in another form leaves those entries null in the products view.

## 4 The job frame a Matsya handler receives

The job frame is one record, the dataclass `Frame` of `frame.py`, built by the processor for each job; the word frame alone names the package. A Matsya handler uses the `bellman` package and the `meaning-map-training` package only through the job frame and imports neither.

| Attribute | What it is |
|---|---|
| `texts` | the seven instruction texts by role key, and the conversation role's when the configuration enables it |
| `guides`, `guide_manifest` | the three guides by short name (`writer`, `reader`, `calculus`) and their entries of the page manifest: the ordered pages and, for a manifest of the form `matsya-guides/3`, each saved page's sections, authored links and tag memberships |
| `settings` | the checked settings, with `roles` as `RoleSettings` records and `ceilings`, the language-model token ceilings, as a `Ceilings` record |
| `call(role, parts, prefix)` | the function that sends a message to the provider: the ordered parts of one message and the number of leading parts marked for the prompt cache; returns the answer with its token counts. It is the method `call` of the fixed caller `ProviderCaller` of `roles.py`, which counts the message's tokens first, refuses a message that would not fit the language model's context window with `PromptTooLong` and a call that would pass a token ceiling with `CeilingReached`, and charges every attempt to the job's token ledger |
| `record`, `progress` | the job's record, begun by the processor, and the job runner's progress callback |
| `index`, `source`, `references`, `earlier` | the reading controller `ReadingController` of `retrieval/context.py`, which the processor builds over the snapshot of the retrieval index the job holds and which is a Matsya handler's only access to the index and to the guides' records: `bind` binds it to the role of an invocation of `prepare` or `write`, `search` makes the invocation's initial search, `reuse` places passages an earlier invocation retrieved, `request_of` and `resolve` examine an answer for the request form and answer a request through the snapshot's `related` and `read` ([The retrieval index](01-the-retrieval-index.md) §9) or the guides' records, `parts` gives the parts it writes into the next message, and `called`, `ordinary` and `end` record the calls, the ordinary answers and why the invocation stopped ([What Matsya reads](02-what-matsya-reads.md) §5); the job's `Source` record; the passages of preparation's initial search; and `earlier`, the job of the same session that this job continues, with its identity, status, source digest, description, questions, formulation and concepts, or `None` |
| `join_parts`, `sha256` | the joining of a message's parts under `===== <label> =====` lines, and the digest function |
| `elaborate_text`, `elaborate_trellis`, `period_joins`, `dossier_lines` | the four functions of the `bellman` package that the frame calls: the elaboration of one text and of a trellis, the joins of a period, and the dossier printer |
| `elaborate_files`, `dossier_of`, `parse_writer_files`, `digest_of`, `profile_equal`, `allowed_declaration_name`, `form_check` (`check_reader_form` in the module), `compare` (`compare_outcomes` in the module) | the functions of `meaning.py`: parse a Bellman-SYM writer's answer into files, elaborate them (`elaborate_files`, which computes the Bellman-SYM elaborator `BellmanSYMDeclaration_to_ElaboratedSemanticObject`), print the dossier with the stage names hidden, compare two elaborations with the comparator of `packages/meaning-map-training` (`compare`, which computes `ElaboratedSemanticObject_comparator`), check a description's form |
| `targets` | the four targets of a job, `stage`, `period`, `trellis` and `recipe`, in the order in which each holds the one before it (`TARGETS` of `meaning.py`), which the Matsya handler `cycle` reads to decide whether the job's target holds the level of the structure the description states |
| `errors` | the exception classes a Matsya handler raises or catches: `ModelAnswerError`, `MeaningRefusal`, `IncompleteResponse`, `PromptTooLong`, `ProviderError`, `ProviderRefusal`, `ProviderRejected`, and the set `STOP_REASONS` |

For a turn of conversation mode the turn runner fills the same record: `index` is the reading controller bound to the turn (§7), `source` is `None`, `record` holds the turn's identifiers, and `call` is the fixed caller's, wrapped so that the turn runner records each call and its events itself; the call list a Matsya handler receives for a turn is its own and no record reads it.

A Matsya handler raises `ModelAnswerError` when a language model's answer lacks the required structure or evidence, with one of the 27 validation codes the program fixes, such as `json_decode`, `judge_quotes` or `writer_input_quote`; the job runner records such an error as `invalid_model_response`.

## 5 How the program loads and checks the module

`configuration.load` runs its checks in a fixed order and stops at the first failure: the files against `manifest.json`; the three guides against their page manifest, the page markers and, for a manifest of the form `matsya-guides/3`, each page's saved digest, its sections' spans and the targets of its available links; `settings.json`; the import of the Matsya handler module under the module name `matsya_configuration_handlers`; and the thirteen signatures, with `conversation_reply` when the settings name the conversation role, each name present and callable with exactly the slot's parameter names in the slot's order, read with `inspect.signature`. Type annotations, default values and return types are not compared, and no other function is checked, so helpers may be added, renamed or removed freely, and a configuration that does not name the conversation role may hold a function named `conversation_reply`, which is then not checked. Before the signatures the loader reads the conversation role's parts together, after the settings' types and before the readers of `roles`, `ceilings` and `reading`: the role's `reading` entry, its entry in `ceilings.roles`, `ceilings.turn`, `conversation_rounds` and `conversation_pages`, then the text `texts/conversation-answer.md`; a part missing with the role, or present without it, refuses the folder naming that part. A failed check raises `ConfigurationRefused`, whose detail names the file or the Matsya handler: when a check fails at the start of a job, the job fails with the code `configuration_refused` and no language model is called; when it fails before the server starts, `matsya-serve` refuses to start. The folder is checked on three occasions on a server: by `matsya-serve` before the server starts, by the application's start-up, and at the start of every job, so an edit to the folder takes effect at the next job. Two commands act on the folder: `python -m matsya_service.configuration manifest <folder> --version <version>` rewrites `manifest.json` from the files present, and `python -m matsya_service.configuration check <folder>` loads the folder as a job would and prints its version and digest, then a line that names the form of the guides' page manifest and says whether its relationship records were checked, or `configuration_refused` with the detail.

## 6 Changing a Matsya handler, adding a helper, adding a slot

To change what a Matsya handler does while keeping its name and parameter names, edit the module, rewrite the manifest with the `manifest` command, and run the `check` command. The package's tests do not load the configuration folder that the service uses: they copy a second configuration kept for the tests under `packages/matsya/tests/fixtures/configuration/`, whose Matsya handler module and eight texts, the conversation role's among them, are byte-identical with the service's folder on 9 October 2026, so a change to the service's module is tested only when the same change is made to the test copy. The test copy's guides are written by the guide builder from the small documentation tree of `packages/matsya/tests/fixtures/documentation/`, which holds a stand-in for each core page and the pages that test the links and tags, under that tree's own construction policy.

Adding a helper needs only that it be written in the module and called from one of the thirteen Matsya handlers, since the program neither calls nor checks it.

Adding a slot, renaming one, changing a slot's parameter names, adding a role and adding a setting are changes to the program; each is made as an amendment of the dev-spec, with a brief for its implementation, and not as a change of the configuration. An optional slot, such as `conversation_reply`, stands in `OPTIONAL_SLOTS` with the role that requires it in `ROLE_SLOTS`, an optional role in `OPTIONAL_ROLES` of `roles.py` and its settings in `OPTIONAL_SETTINGS`, and the loader checks them only in a configuration that names the role. A new slot needs its entry with ordered parameter names in `SLOTS` of `configuration.py`, a call to it from the program or from another Matsya handler, the function in every configuration's module including the test copy, rewritten manifests, and a new row in the Matsya handler table of the dev-spec's §5.4. A new role needs its key in `ROLES` of `roles.py`, a text `texts/<role key with hyphens for underscores>.md`, an entry in the `roles` object of `settings.json`, and a Matsya handler that calls `call(frame, "<role key>", parts, calls, None)`. A new setting needs its key and type in `SETTINGS` of `configuration.py`, the key in `settings.json`, and a Matsya handler that reads `frame.settings["<key>"]`, because the loader refuses a key present in only one of the two.

A trained candidate is a new configuration folder with its own manifest and version, and a candidate whose Matsya handler module differs from its parent's is recorded as a commit together with the run that accepted it; the rule is the governing document's §5.

## 7 One turn of conversation mode

A configuration that enables the conversation role, `conversation_answer`, answers a question asked in a session in a **turn**, which the route `POST /v1/sessions/{session_id}/turns` appends to the session as an entry of the user and records as `queued`. The turn runner, `TurnRunner` of `conversation.py`, which the program holds and a training pass does not change, then loads the configuration, fixes the turn's snapshot of the index, builds the turn's language-model token ledger, binds the reading controller ([What Matsya reads](02-what-matsya-reads.md) §8), reads again the passages the previous turn cited, elaborates a stage file the request names, and calls `conversation_reply(frame, turn, calls)`. `turn` is the record `Turn` of `conversation.py`: the turn's identifier and session, the question and its entry number, the named fields, the elaborated stage file or its refusal, never the file's text, the session's entries up to the question, the previous turn's decision list, the retained passages and the snapshot's digest.

The starting `conversation_reply` places the guide pages `conversation_pages` names, which the controller reports as `frame.index.pages`, after the instruction text as the cached prefix; makes one search from the question through `frame.index.search`; has the controller supply, with `frame.index.supply_job`, the outputs of the job the conversation discusses, which the turn runner names: the session's selected job or else its latest job that holds a record and was current at its end, never a job that was not current unless the selection names it; the label of each output of a job that was not current states the version of the session's text the job was built from and the version the text is at now, the turn's result names the job under `job`, and the job's stage files are never supplied this way (AMD-MAT-008 §§3–4); and, for a stage file that elaborated, calls `prose_write` on the elaborated semantic object, so that the role receives the dossier and the prose writer's description of it. It then calls the role through `_requests`, as `prepare` and `write` call theirs, so that every answer is examined for the request form before any other parser and a request is resolved by the controller within the role's request rounds. An ordinary answer is read as one JSON object with `_json_answer` and checked: its status and fields, each citation with `frame.index.check_citation`, the check the turn runner makes again, and the form of each item of the decision list. A failed answer is sent back with `your previous answer` and `the faults of your previous answer` until `conversation_rounds` answers have been given. The Matsya handler returns `answered` with the answer, and with `submit_job` when the role starts a job at the user's request, checked against `cycle_maximum` (AMD-MAT-009 §3), or `needs_input` with the role's questions, each with its citations and decision list, or `incomplete` with `request_rounds_exhausted` or `conversation_rounds_exhausted`, no citation and the previous decision list, and records why the invocation stopped with `frame.index.end`.

The turn runner checks the return (AMD-MAT-006 §7): a return of another form ends the turn `failed` with `processing_failed`; a citation of material not supplied in the turn, or with a quote absent from it, ends the turn `incomplete` with `unsupported_citation`; an `incomplete` status must agree with the turn's record of allowances, ceilings and calls; and a call refused at a ceiling, or one the provider could not complete, ends the turn `incomplete` whatever `conversation_reply` returns or raises. It decides whether the turn is current, appends the answer, or the questions, as entries whose origin is the turn and which reply to the question, and stores the record. The turn's states, statuses, reasons, fixed sentences and record are the program's, so that a Matsya handler can change what the role reads and how its answers are repaired, but not the permissions, the snapshot, the limits or the acceptance of an answer.
